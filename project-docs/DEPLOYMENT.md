# Production Deployment Runbook

## Target architecture

```text
Browser
  -> Render Python web service (Frankfurt)
  -> Gunicorn (`wsgi:app`)
  -> Flask
  -> Neon PostgreSQL (Frankfurt, direct TLS connection)
```

The initial deployment uses one conservative Gunicorn worker with two threads. It uses Neon's direct PostgreSQL connection, not a connection pooler, because the application depends on PostgreSQL transaction advisory locks and initial traffic is small. SQLite remains suitable for automated tests and limited local development only; production rejects it.

Do not create infrastructure from this repository stage. The `render.yaml` Blueprint describes one free demonstration web service and no database resource.

## Runtime and environment

Render uses Python `3.14.2`, pinned in `.python-version`. Configure these names in the Render dashboard without placing values in source control:

- `DATABASE_URL` - direct Neon PostgreSQL TLS URL, including the provider's required query parameters
- `SECRET_KEY` - generated by Render
- `APP_ENV=production`
- `PYTHONUNBUFFERED=1`

Temporary first-deployment variables:

- `INITIAL_ADMIN_USERNAME`
- `INITIAL_ADMIN_FULL_NAME`
- `INITIAL_ADMIN_PASSWORD`

All three bootstrap variables must be supplied together or all omitted. Delete them from Render immediately after the first successful deployment. Never copy production values into `.env.example`, logs, screenshots, issues, or command arguments.

The application normalizes only `postgres://` or `postgresql://` to the installed `postgresql+psycopg://` driver scheme and preserves the remainder, including TLS query parameters. Production fails fast for missing configuration, placeholder secrets, SQLite, or non-PostgreSQL URLs.

Neon may show a pooled connection string by default. In Neon's connection details, disable the connection-pooling option and verify that the displayed hostname does not contain `-pooler`. Copy the resulting direct TLS URL without manually extracting, rewriting, or exposing its credentials. Retain `sslmode=require`, `sslmode=verify-ca`, or `sslmode=verify-full`; also retain `channel_binding=require` whenever Neon supplies it. The same direct URL is used by startup migrations and the running application during the initial deployment.

## Build and startup

Render builds with:

```sh
pip install -r requirements.txt
```

It starts with:

```sh
sh scripts/render-start.sh
```

The fail-fast startup sequence is:

1. Validate that `SECRET_KEY` and `DATABASE_URL` exist without printing them.
2. Run reviewed migrations once with `flask --app wsgi:app db upgrade`.
3. Run the idempotent `seed` command.
4. Run the optional idempotent `provision-admin-from-env` command.
5. Remove all three `INITIAL_ADMIN_*` values from the process environment.
6. Replace the shell process with Gunicorn bound to Render's `PORT`.

Migration, seed, or bootstrap failure prevents Gunicorn from starting. Startup never generates migrations, downgrades, resets data, or runs initialization once per worker. The existing Alembic revision history must be reviewed and committed before deployment.

## Seed and Administrator bootstrap

The seed command only ensures the approved school classes, Smart Class 1 through 3, and singleton SystemSettings row exist. Repeated execution does not duplicate, delete, reactivate, or reset existing records or create operational data.

The private bootstrap command creates one active `ADMIN` account with a securely hashed temporary password and `must_change_password=true`. It is a no-op when the same Administrator already exists and never resets that account. It fails if the username belongs to another role or if a different Administrator already exists. It never prints the password or hash. The three bootstrap variables are available to this one-time command, then the startup script unsets them before Gunicorn starts so the long-running application and its workers do not inherit them.

After the first successful login and forced password change, remove all three `INITIAL_ADMIN_*` variables and redeploy to confirm ordinary idempotent startup.

## Health and smoke checks

Render uses `GET /health`. It returns only `{"status":"ok"}` without database, user, notification, migration, environment, or version checks.

After a live HTTPS URL exists, run:

```sh
python scripts/smoke_test.py --base-url https://example.onrender.com
```

The non-mutating script checks health, the public schedule, login, a protected route, the custom 404 response, and absence of obvious debugger output. It uses no credentials and performs no POST requests. Then manually test all four roles, temporary-password change, public privacy, queue behavior, scheduling conflicts, notifications, reports, static assets, and safe error pages.

## HTTPS, cookies, static files, and logging

Render terminates TLS. Production trusts exactly one forwarded proxy hop for client address, scheme, and host; development and tests do not. Production cookies are Secure, HttpOnly, and SameSite=Lax, including remember-me cookies. Flask serves committed static CSS and JavaScript; no uploads or business data use Render's ephemeral filesystem.

Application and Gunicorn logs go to stdout/stderr. Never log passwords, hashes, cookies, sessions, CSRF tokens, `SECRET_KEY`, `DATABASE_URL`, complete forms, private booking reasons, or unnecessary rejection/block reasons. Production keeps debugging disabled and uses the database-independent generic 500 page.

## Deployment and rollback procedure

1. Create Neon and Render resources in Frankfurt.
2. Record the exact deployed Git commit and current Alembic head.
3. Configure environment variables in Render.
4. Deploy and inspect build, migration, seed, bootstrap, and Gunicorn logs for safe success messages.
5. Check `/health`, run the smoke script, then perform manual role smoke tests.
6. Remove bootstrap variables after the first successful deployment and redeploy.

For application rollback, redeploy a previously recorded compatible commit. Never run an automatic downgrade or delete/reset production tables. Before schema-changing deployments, use an available Neon restore point, branch, export, or snapshot and verify its retention. Free tiers may sleep, have capacity limits, and may not provide the backup retention, interactive shell access, availability, or recovery guarantees required for operational school use.

Do not enter real school, staff, or booking data until the institution authorizes production use and access control, retention, backup ownership, restore testing, incident response, and recovery objectives are approved. Milestone 11B must perform and record the actual Render/Neon provisioning, production migration, bootstrap, HTTPS, backup, restore, and live smoke checks; none are claimed by this repository-only preparation.
